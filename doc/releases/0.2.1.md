# Minesport 0.2.1 — World Cache & Export Worker Rewrite

> **Status: in development.** This document tracks the intended 0.2.1 architecture and the work being landed during the 0.2.1 cycle. Items described as targets are not considered shipped until their implementation and compile/test gates are green on `main`.

Minesport 0.2.1 is focused on removing repeated Minecraft-world parsing and reducing the amount of work that requires a Minecraft runtime. The release separates three concerns that had become too tightly coupled in 0.2.0:

1. **World Cache (WC)** — what exists where in the selected world.
2. **Engine / Model Cache** — what a block state looks like when it can be resolved from assets or an existing baked-model snapshot.
3. **Export Worker** — runtime-only Minecraft data that cannot be reproduced exactly from world files and static assets alone.

The goal is that ordinary selection, preview and Litematica work never need to re-open large `.mca` files after the background world cache is ready, and most OBJ/glTF exports never need to launch a Minecraft runtime at all.

## Bridge rename → Minesport Export Worker

The component previously called the **Minesport Bridge** is being renamed and narrowed into the **Minesport Export Worker**.

The intended artifact naming is version-oriented rather than product-release-oriented:

```text
minesport-export-worker-<loader>-<minecraft-version>.jar
```

Examples:

```text
minesport-export-worker-fabric-1.21.10.jar
minesport-export-worker-forge-1.20.1.jar
```

Loader-specific directories may be used in packaged builds so the logical worker name can remain shorter where appropriate.

The Export Worker is **not** the world parser and is **not** the exporter. Its responsibility is to ask the real Minecraft client/model environment for runtime-only information that Minesport cannot guarantee from files alone.

The worker remains useful for:

- Minecraft's final `BakedModel` output;
- all registered block-state variants;
- baked quads for unculled and directional faces;
- exact per-quad UV coordinates;
- texture identifiers/sprite references;
- tint indices;
- shade flags;
- loader/mod custom model implementations;
- runtime/custom model loaders that do not have a static JSON representation;
- loader/version compatibility boundaries where Minecraft's client APIs differ.

The worker should **not** own:

- `.mca` parsing;
- world selection;
- chunk caching;
- Litematica generation;
- OBJ/glTF writing;
- mesh optimization;
- ordinary JSON blockstate/model parsing;
- ordinary mod-JAR texture extraction;
- 2D or 3D selection logic.

## Exact Export Worker lifecycle

0.2.1 defines the runtime lifecycle explicitly so a disposable Minecraft process does not remain alive after its useful work is finished.

```text
Need exact runtime-only models
        ↓
Check model cache fingerprint
        ↓
Cache hit? ── yes ──→ use registry.data; launch nothing
        │
        no
        ↓
Start disposable Minecraft Export Worker runtime
        ↓
Initialize loader + installed mods + resource packs
        ↓
Wait for Minecraft resource/model manager to finish baking
        ↓
Enumerate required registered BlockStates
        ↓
For each state:
  - state properties
  - BakedModel
  - unculled quads
  - DOWN / UP / NORTH / SOUTH / WEST / EAST quads
  - vertices + UVs
  - texture/sprite id
  - tint index
  - shade flag
        ↓
Stream model snapshot to Minesport
        ↓
Receiver validates header, fingerprint, counts and snapshot integrity
        ↓
Atomically publish registry.data / model cache
        ↓
CAPTURE COMPLETE
        ↓
SHUT DOWN MINECRAFT WORKER IMMEDIATELY
```

The worker does **not** wait for an export to finish. Once the complete model snapshot has been received and committed, the Minecraft process has no remaining responsibility and must exit. If graceful shutdown does not complete within a short timeout, Minesport may terminate the disposable worker process.

No Minecraft world needs to be opened for this process. The worker only needs the client resource/model environment to reach the point where the final baked models exist.

A model snapshot is keyed by inputs such as:

- Minecraft version;
- loader and loader version where relevant;
- installed mod fingerprint;
- resource-pack fingerprint;
- model-cache schema / Export Worker protocol version.

As long as those inputs do not change, later exports reuse the saved baked-model cache and do not launch Minecraft again.

## Offline-first model resolution

Before starting an Export Worker, the Engine should resolve everything it safely can from files.

Minesport already has resolver infrastructure capable of reading mod JAR assets directly, including:

```text
assets/<namespace>/blockstates/*.json
assets/<namespace>/models/*.json
assets/<namespace>/textures/*.png
```

0.2.1 formalizes this as the first model path:

```text
selected block states
        ↓
model cache lookup
        ↓
static/offline asset resolver
        ↓
resolved? ── yes ──→ geometry
        │
        no
        ↓
Export Worker runtime fallback
```

The runtime worker is therefore a **truth/fallback layer**, not a mandatory step for every export.

## World Cache (WC)

The world cache is a persistent, disposable, rebuildable representation of **world state**, not rendered geometry.

### Cache root

The intended user cache layout is:

```text
<user>/.cache/kastrick's_software/minesport/wc/
  <launcher_name>/
    <instance_name>/              # only where launcher context needs it
      <world_name>/
        diem/
          overworld/
          nether/
          end/
```

On Windows `<user>` is the user's profile directory.

Only the three vanilla dimensions are first-class in 0.2.1:

- Overworld;
- Nether;
- End.

**Modded/custom dimensions are deferred to a later release.** Their path conventions, lifecycle and storage requirements need a separate compatibility design rather than being guessed into 0.2.1.

### `.chunk` files are parsed and uncompressed

A `.chunk` cache file must **not** merely copy the compressed payload from an Anvil region file. The point of WC is to pay the `.mca` decompression/NBT decode cost once in the background and keep an immediately readable Minesport-native world-state representation.

A logical cached chunk contains data such as:

```text
schema/version
Minecraft DataVersion
dimension
chunk X
chunk Z
source-region identity/timestamp/fingerprint

palette / canonical block states
Y sections
block-state indices
block entities
entities where available
scheduled block ticks
scheduled fluid ticks
other world-state metadata needed by exporters/previews
```

Geometry, baked quads and texture pixels do **not** belong in WC.

### Source of truth

Minecraft's save remains authoritative:

```text
Minecraft .mca = source of truth
Minesport WC   = disposable derived cache
```

If WC is missing, stale, corrupt, or schema-incompatible, Minesport rebuilds it from the world instead of attempting to repair the Minecraft save.

### Incremental background updates

Selecting a world starts a low-priority WC watcher/indexer in the background.

The indexer should use cheap region metadata/header checks first and only re-parse chunks that actually changed. When a world changes, Minesport updates only affected `.chunk` records and deletes cached chunks that no longer exist in the source world.

Selection-sensitive work gets higher priority than background indexing. If the user selects an area whose chunks have not yet been cached, those chunks are moved to the front of the indexing queue instead of forcing the user to wait for the entire world.

## Litematica fast path

Litematica does not need rendered geometry.

Once WC is ready, the Litematica pipeline becomes:

```text
2D selection
    ↓
required cached chunk coordinates
    ↓
read uncompressed WC state
    ↓
clip X/Y/Z or bubble selection
    ↓
block-state palette
block entities
entities
scheduled block/fluid ticks
    ↓
write .litematic
```

The Export Worker, runtime model registry, Minecraft model manager and mesh geometry pipeline are intentionally absent from this path.

This is expected to remove the repeated `.mca` scan/decompression cost that made small Litematica selections take disproportionately long in 0.2.0.

## OBJ / glTF export path

OBJ/glTF still require geometry, but WC eliminates repeated world decoding:

```text
WC selected world state
        ↓
unique block states
        ↓
existing baked-model cache
        +
offline asset resolvers
        ↓
missing runtime-only states?
   no ──────────────→ build geometry
   yes
    ↓
Export Worker capture
    ↓
update model cache
    ↓
build geometry
    ↓
cull / optimize / translate
    ↓
OBJ / glTF
```

The world cache and model cache intentionally have different invalidation rules:

- WC changes when the world changes.
- Model cache changes when Minecraft/mod/resource-pack/model inputs change.

Placing a block should not invalidate every baked model. Installing a mod should not require every unchanged world chunk to be re-decoded.

## 2D becomes the authoritative selector

0.2.1 removes the concept of 3D selection as a second competing editor.

The 2D world view owns selection state:

- box X/Z selection;
- bubble selection;
- Y minimum/maximum controls;
- selection move/resize;
- chunk-grid awareness where useful;
- exact/custom masks when supported.

This keeps one authoritative selection descriptor for preview, preflight and export.

## 3D becomes a live preview / thumbnail

The 3D viewport becomes a smooth retained preview of the current 2D selection rather than a point-A / point-B voxel picker.

Removed from 3D selection mode:

- LMB point A;
- RMB point B;
- click-to-confirm selection;
- selection resizing with 3D-specific shortcuts;
- clear-selection shortcuts owned only by the 3D view;
- crosshair/picking behavior whose only purpose was editing selection bounds.

Retained for preview:

- orbit;
- pan;
- zoom/dolly;
- fit/center;
- preview lighting/render settings;
- smooth retained scene updates.

Selection edits are debounced/latest-wins so rapidly dragging the 2D box does not start a full preview rebuild for every mouse pixel. Only newly required cached chunks/sections should be added where possible, and removed chunks should be dropped from the retained preview scene.

## Export progress and terminal-state cleanup

The 0.2.1 line continues the export lifecycle work started during late 0.2.0 development:

- fake weighted percentages are replaced by real counted work where totals exist;
- unknown-total phases use indeterminate progress;
- chunk decode reports identify the current chunk/stage instead of leaving stale region text on screen;
- Litematica writes use staged `.part` output and publish the final filename only after the file is complete;
- the final backend `done` event is emitted immediately after the final file is published;
- the desktop may hold visual progress at 99% only long enough to finish the loader's completion animation;
- completion animation must not imply that backend work is still running.

## Minesport loader animation

The task loader is being treated as a branded state machine rather than a generic spinner.

Working state:

- nine visibly separated dots;
- no permanent center ball during normal travel;
- rollercoaster-style travel with deliberate top pauses;
- repeat travel while the task is active;
- a final one-by-one curved inward path where the leading dot enters the center first and each following dot uses the same path;
- the center mass only exists once dots actually merge;
- an unfinished task does not show the final Creeper face.

Completion state:

- backend completion arms the success state;
- visual progress may remain at 99% while the current motion cycle reaches a safe completion point;
- the merged mass performs the final balloon/pop transformation;
- black negative-space Creeper eyes and mouth appear only for successful completion;
- the UI reaches 100% only after the completion reveal finishes.

## Scheduled tick preservation

Litematica exports preserve scheduled block and fluid ticks where the source world provides them. Selection filtering applies to tick coordinates the same way it applies to blocks/entities so exported tick payloads do not silently refer to locations outside the selected region.

## Fresh build semantics

`--fresh` is intended to mean a genuinely fresh Minesport build without needlessly redownloading every dependency:

- remove Minesport build outputs;
- remove repository/project-local Gradle state;
- run Gradle `clean build --rerun-tasks --no-build-cache` in fresh mode;
- preserve global dependency download caches;
- preserve Cargo registry/download caches;
- preserve downloaded JDK/toolchain caches.

This prevents stale Engine/worker artifacts from surviving a source change while keeping rebuilds practical.

## Naming cleanup

0.2.1 begins replacing old terminology where it describes obsolete architecture:

- **Bridge** → **Export Worker** for the runtime Minecraft-facing component;
- **runtime registry/cache** → **model cache** where the stored data is specifically baked model geometry/state information;
- **world cache / WC** exclusively refers to parsed world-state chunks;
- 3D **selector** → 3D **preview**.

Source package/class names may migrate incrementally to avoid turning one release into a dangerous all-at-once rename. Artifact names and user-visible terminology should move first; internal compatibility identifiers can retain aliases while older cache/recipe formats are migrated.

## Compatibility scope for 0.2.1

0.2.1 keeps the existing compatibility direction for supported Fabric/Forge/NeoForge/Quilt targets while refactoring where runtime data is used.

The world cache is intended to be loader-independent because Minecraft world-state decoding is based on save data rather than rendered geometry. Export Worker compatibility remains loader/version specific because baked-model APIs and mod runtime behavior are loader/version dependent.

### Explicitly deferred

The following are not requirements for the initial 0.2.1 WC rollout:

- arbitrary modded/custom dimensions;
- guaranteed offline reproduction of every custom Java renderer;
- replacing Minecraft's baked-model environment for mods that generate geometry in code;
- storing geometry inside WC;
- using WC as a replacement/source of truth for the Minecraft save.

## Intended 0.2.1 outcome

After the first background indexing/model preparation pass, the common workflow should feel approximately like this:

```text
Select world
    ↓
2D map immediately usable from existing map/cache data
    ↓
WC updates changed chunks in background

Select build in 2D
    ↓
3D thumbnail updates from cached world state

Litematica export
    ↓
WC → crop → Litematica writer
    ↓
no Minecraft launch

OBJ/glTF export
    ↓
WC → model cache/offline resolver
    ↓
Export Worker only if runtime-only model data is missing
    ↓
worker captures models and dies
    ↓
geometry/export continues without Minecraft
```

The key 0.2.1 rule is simple:

> **World data is decoded once and cached as world state. Model data is resolved once and cached as model data. Minecraft only runs when Minesport genuinely needs Minecraft itself to answer a runtime-only model question.**
