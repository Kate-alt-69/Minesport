# Page 90 — Runtime Model Cache

The Runtime Model Cache exists so Minesport can ask **Minecraft itself** what registered block states and baked models look like instead of trying to reverse-engineer every mod renderer from static JSON forever.

For normal supported Fabric exports, this cache is part of the **Export pipeline**. You do not have to remember to generate it first.

## Why Minesport needs it

Vanilla/resource-pack JSON is enough for many blocks, but modded Minecraft can register blocks and models through code. A block may also have multiple baked boxes/quads or state-dependent geometry that is safer to read from Minecraft's own client model system.

The runtime worker therefore captures registry/model information such as:

- registered block IDs;
- registered block states/properties;
- baked quad vertices;
- material/texture identifiers;
- geometry/state distinctions;
- block-light/luminance states where available.

Texture **image bytes are not duplicated into the model cache**. Minesport keeps texture identifiers and resolves the actual PNG/JPEG data separately from resource packs, mod JARs, local vanilla assets, or official Mojang/Piston recovery.

## What happens when you click Export

For a supported Fabric world:

1. Minesport identifies the Minecraft version and selected mod set.
2. It calculates a fingerprint for the runtime-model cache.
3. If a matching valid cache already exists, Export reuses it.
4. If the cache is missing/stale, Minesport starts an isolated exact-version worker.
5. The worker loads the selected Fabric mods and Minecraft client resources/models.
6. Minesport's Bridge dumps the registered state/model information.
7. The cache is stored under Minesport's rebuildable user-cache location.
8. The disposable worker directory is removed after a successful capture.
9. Export continues automatically.

Progress belongs in Minesport's **bottom task notification** instead of blocking the main world UI.

## Does this launch my real Minecraft profile/world?

No. The worker is deliberately separate from the normal launcher/player session.

It receives copied mod/config inputs in a disposable runtime workspace. It must not open the selected world save for gameplay and is intended to be effectively read-only with respect to the user's source instance/world.

The Minecraft client resource/model bootstrap is still used because that is where Minecraft bakes the client block models. Minesport hides the worker window as early as the relevant client bootstrap permits and exits after registry capture.

## Why not just parse every mod JAR statically?

Minesport still has static resolvers, but code-driven registration can make static parsing incomplete. The runtime cache lets the exact modded client tell Minesport what states/models were actually registered.

Static resolvers remain useful as fallbacks and for formats/data that do not require booting a client model environment.

## When is the cache regenerated?

A different relevant Minecraft/mod fingerprint should produce a different cache. Updating/removing/adding relevant mods or changing Minecraft versions can therefore trigger regeneration.

The point is to pay the expensive model-bootstrap cost **once per matching environment**, not on every export.

## Where is it stored?

On Windows, rebuildable Minesport cache data targets:

`%USERPROFILE%\.cache\kastrick's_software\minesport\`

Runtime registry snapshots live beneath that cache root rather than bloating LocalAppData with another application-state folder.

## Manual controls

Manual **Generate / Rebuild / Clear / Cancel** controls belong in **Minesport Settings → Advanced → Runtime Model Cache**.

Use them when debugging or when you explicitly want to invalidate/rebuild a cache. They are not supposed to be a required normal-export ritual.

## What if the worker fails?

Minesport should preserve useful worker diagnostics instead of deleting the only evidence with the disposable directory. Use **[Page 20 — Troubleshooting](20.md)** and include the preserved runtime-worker log when reporting the problem.
